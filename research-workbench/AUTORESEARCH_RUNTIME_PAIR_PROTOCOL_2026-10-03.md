# Runtime-feedback experiment — one finite matched pair

Purpose: test whether the corrected lower-is-better instructions and measured runtime history produce valid, useful fixed-time candidates. Compare memory on/off from the same 7,295,232-parameter incumbent, same proposer model/digest, temperature 0.3, seed 20261003, protected byte-language-model code and TinyStories data. Memory arm receives the frozen 17-record development index; no-history receives none. Both get the same incumbent score and static parameter profile. No arm sees newly generated proposals or outcomes from its peer.

One pair is a development feasibility comparison, not evidence of statistically reliable retrieval benefit. TinyStories training contains 134,217,966 bytes, validation 2,097,193; fixed 256-byte context and existing validation prefix are unchanged. Training seed remains 20260929. Lower validation bits/byte is better. The previous incumbent score is 0.9121882523777711 and is historical, not a concurrently rerun control. Report each candidate's score, pair difference, parameter count, steps, runtime, GPU model/memory, hashes, invalid attempts and independent checkpoint verification.

Freeze before sampling: four local generation calls maximum, two attempts per arm only for sampled static-invalid proposals, each request 300 seconds maximum; abort on transport failures. One accepted GPU candidate per arm at most. Two 22-minute RTX3090 allocations maximum (44 GPU-minutes), concurrency at most two, 1200 training seconds each, no requeue or scheduler-failure restart. Proposed code passes existing static numeric-edit boundaries before a no-network Bubblewrap execution with read-only data/evaluator and only per-cell output writable. Allow at most 250MB total new output. Preserve prior ledgers and any partial/failed result; no budget extension.

Local proposals start only after the separate article-model campaign ends so the local server has one caller. Expected time: local generation up to 20 minutes plus about 22 minutes of GPU work and queue wait. The cheaper choice is proposal validity only; it cannot measure model quality. This finite protocol follows the user's authorization to continue larger runs.
