## Repair mode: candidate first pilot

The [BugsInPy benchmark](https://github.com/soarsmu/BugsInPy) has real Python bugs with buggy/fixed commits and test scripts. A reference checkout was inspected at commit `11c5f1eea954a42132cfd06bf257766a7963e0fd` (501 `bug.info` files in that checkout). Three small PySnooper cases, IDs 1–3, each specify Python 3.8.1 and a test file, so they are plausible harness smoke tasks. This is a **proposed** task set, not a completed quality screen. The benchmark metadata includes `bug_patch.txt`; those answer patches must be absent from the agent's worktree/search index and available only to the evaluator.

**Static task-screen update, 28 September:** PySnooper bugs 1 and 2 start from the **same buggy commit** (`e21a3116...`) but have different fixed commits and tests; they are useful for harness coverage but are not independent repository examples. The three targeted tests are `test_chinese`, `test_custom_repr_single`, and `test_file_output`. Bug 2's setup installs `python_toolbox`; bug 3 installs `decorator`. The pinned BugsInPy Dockerfile starts from Python 3.12 even though these bug records request Python 3.8.1, so a successful container build alone would not prove the specified reproduction environment. This screen inspected metadata/scripts only; it did not execute code or inspect the hidden answer patches for task construction.

First verify each buggy commit fails its benchmark test and the fixed commit passes inside an isolated container. Then freeze a task statement from the failing test/error and source docs without showing the fixed patch. Run the same model, tool budget, timeout, and three tasks with and without repository retrieval. Report tasks resolved, regressions, time, token/tool cost, and cited file relevance. Three cases can establish harness behavior, not a statistically persuasive retrieval advantage; expand to a predeclared varied task set only after this smoke stage.

The local Docker daemon was not running on 27 September 2026, and the Mac had about 16 GiB free. The [official SWE-bench Docker setup](https://github.com/SWE-bench/SWE-bench/blob/main/docs/guides/docker_setup.md) calls for at least 120 GB free and is unsuitable on this local disk. A cluster container runtime or a provisioned host could make the BugsInPy pilot practical; no generated patch should run in an unsandboxed user checkout.

## Experiment mode: following the same discipline

Select a small fixed training task only after the cluster hardware inventory and the ECG/corpus protocols are settled. Freeze data manifest, `prepare.py`, metric, one `train.py`, a short per-run time budget, and at most three candidate runs in the first batch. The unchanged baseline goes first. Retrieval-enabled candidate selection searches only prior development runs; an otherwise identical no-memory arm tests whether the new memory layer helps. Do not infer a benefit from the existence of a search index alone.

The original 27 September proposal had not run a benchmark. The 28 September harness screen executed tests on buggy and fixed code, but no coding agent, generated patch, retrieval comparison, or ML experiment has run.
