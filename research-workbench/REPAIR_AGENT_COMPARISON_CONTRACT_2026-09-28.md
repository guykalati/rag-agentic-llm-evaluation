# Project 2: repair-agent comparison contract (prepared, not run)

## Purpose and current evidence

The first agent run should establish that a model can edit a real buggy checkout, submit a small patch, and pass the same isolated evaluator in both arms. It would also exercise our original repository-evidence retrieval layer. It is **not** a study of a general retrieval benefit: two cases come from PySnooper and a third candidate comes from tqdm under a deliberately modified runtime. [The harness screen](REPAIR_HARNESS_SCREEN_RESULT_2026-09-28.md) records the actual test results.

The two benchmark-runtime development cases are BugsInPy PySnooper **2** (`custom_repr`) and **3** (`output_path`), using the pinned commits and Python 3.8.1 in the preparation/screen scripts. Case 1 is ineligible because its targeted test passed on the buggy revision. A third, different-repository development case is **tqdm 3 under a modified Python 3.8.1 runtime**: its buggy/fixed `test_bool` pair was screened successfully, but the BugsInPy-specified Python 3.6.9 environment could not be created within two capped jobs. It must be identified as a modified harness task, never as an exact BugsInPy reproduction. Freeze whether to use two exact-runtime cases or the mixed three-case development set before comparing arms; do not add a case after seeing agent results.

## Retrieval feasibility probe

I built [the FTS index](implementation/repo_evidence.py) over each prepared candidate tree, which contains buggy implementation and visible fixed-revision tests but no Git history or answer patch. Case 2 indexed **112** fifty-line chunks. Searching `custom_repr` returned two chunks of `tests/test_pysnooper.py`; the buggy implementation has no `custom_repr` symbol, so the result provides a test clue but does not directly point to the `Tracer.__init__` implementation. Case 3 indexed **21** chunks. Searching `output_path` returned a test chunk and `pysnooper/pysnooper.py` at the failing `open(output_path, 'a')` line. This is a deterministic retrieval check, **not** evidence that retrieval improves repair success.

## Proposed first run

| Item | Frozen value for the first smoke |
| --- | --- |
| Cases | Minimum smoke: PySnooper 2 and 3; two cases × two arms = four independent agent attempts. Optional modified-harness extension: add tqdm 3 under Python 3.8.1, giving six attempts total. Choose the set before launch. |
| Arms | Same model and instructions. One arm receives a deterministic `repo_evidence.py` search result derived only from the task statement; the other receives no injected result. Native code inspection remains available in both arms. |
| Order | For each case, assign arm order with a recorded random seed before launch; each attempt starts from a fresh byte-verified buggy candidate. |
| Agent edits | Implementation files under that attempt's candidate checkout only. The visible tests, evaluator, environment, and task text are immutable. |
| Task text | Failing test path and exception from the frozen screen, plus the public repository description; no fixed source, `bug_patch.txt`, or commentary that reveals the solution. |
| Agent budget | One attempt per case/arm; at most 15 minutes and 20,000 model output/input tokens per attempt, with exact model/version recorded at launch. No retries chosen after seeing a score. |
| Evaluation | Frozen targeted pytest command first, then the corresponding main test file: `tests/test_pysnooper.py` for either PySnooper case or `tqdm/tests/tests_tqdm.py` for tqdm. Use the same Python 3.8.1 sandbox, a 45-second target cap and a 120-second regression cap. Save exit code, logs, patch, changed-file list, tool/model token counts, and wall time. |
| Primary outcome | Number of cases whose targeted test and regression suite both pass (out of the preselected two or three). Report each case/arm separately; do not report a statistical effect from such a small set. |
| Secondary outcomes | Targeted-test pass, regression count, elapsed time, tokens, number of tool calls, and whether retrieved files included the final edited source. |

The [fixed-revision regression screen](implementation/repair_regression_results_2026-09-28.tsv) completed as Slurm job 21726345 in five seconds: PySnooper case 2 had 31 passed, case 3 had five passed, and tqdm had 55 passed plus one skipped. [Logs](implementation/repair_regression_logs_2026-09-28) are saved. The targeted test already fails on each buggy revision; these fixed suites establish that the proposed regression commands are runnable before any agent edits. The retrieval arm is a **prompt-context comparison**, not a clean test of retrieval access, because a coding agent may search the checkout in either arm. A broader claim would need more independent repositories, a preregistered task list, and a controlled tool interface. The modified-runtime tqdm case improves repository diversity but remains too small for a persuasive aggregate claim.

## Isolation gate before any model call

The local Codex CLI's `--sandbox workspace-write` limits writes; it is not evidence that the model cannot **read** answer patches elsewhere on the host. The prepared local reference repositories, fixed evaluator trees, and BugsInPy metadata are readable from the current host, so merely setting the candidate directory as the working directory is insufficient. Repeated candidate-whitelist probes with macOS `sandbox-exec` aborted even for `/bin/cat`; an unrestricted profile worked. We therefore do not use that route for an agent run.

The new [candidate gateway](implementation/repair_gateway.py) and [function-call controller](implementation/repair_agent.py) give the model only bounded listing/reading, one-match implementation edits, and fixed `target`/`regression` requests. They do not expose a shell, host filesystem path, arbitrary test command, SSH credential, or API key. The trusted [cluster bridge](implementation/repair_eval_bridge.py) sends only the candidate to a private remote run and invokes a fixed no-network [Slurm evaluator](implementation/run_repair_candidate_eval.sbatch); the evaluator is never mounted in that test. A live unchanged-buggy integration check, [job 21727533](implementation/repair_gateway_smoke_2026-09-29), reproduced tqdm's expected TypeError. Twenty-three local checks include traversal, symlink, test-edit, invalid-tool, fake-model, transport-failure, and multiline-edit boundaries. The [initial local-model development smoke](REPAIR_AGENT_LOCAL_SMOKE_2026-09-29.md) found an edit-format failure; after a narrow gateway fix, [one fresh no-hint attempt](REPAIR_AGENT_FIRST_SUCCESS_2026-09-29.md) passed PySnooper case 3 target and regression checks. This validates a real candidate patch loop but remains a development case, not a retrieval comparison. [OpenAI's function-calling documentation](https://developers.openai.com/api/docs/guides/function-calling) describes the application-owned tool loop, and its [sandbox security guidance](https://developers.openai.com/api/docs/guides/agents-api/environments/security) recommends keeping application credentials outside agent-executed environments.

Do not copy an authenticated Codex session or API key into a cluster job. For the chosen tool-gateway route, record the exact model, request/response usage, file and test calls, attempt directory, and final independent test outcome. The current local process has **no `OPENAI_API_KEY`**; the installed local Ollama model is available through the same gateway but its service stopped during a retry. Codex app sign-in is not being extracted or reused as an API key.

## Cost and decision point

The planned cluster evaluator jobs use CPU only; the local Ollama development smoke used the Mac GPU. The controller stops once measured usage reaches **20,000 tokens per attempt**, though one final response may overshoot that threshold; four attempts are planned for two cases or six for the modified three-case extension. These are intended limits, not measured costs or strict billing guarantees. The exact monetary cost depends on the selected model and account. The established cluster Python 3.8.1 environment is about 409 MB. Two attempted Python 3.6.9 setup jobs consumed their 15- and 12-minute CPU wall-time caps without producing a usable interpreter; the 3.8.1 exploratory screen completed in four seconds. The regression baseline and candidate-only bridge are now checked. The remaining gates for a comparison are provider stability, a frozen final controller, selected task set/model, and final run approval. The two-case engineering smoke remains a cheaper alternative with no retrieval-performance claim.
